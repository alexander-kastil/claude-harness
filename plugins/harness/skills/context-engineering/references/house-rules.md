# House rules: the full text and incidents

Moved verbatim from `~/.claude/CLAUDE.md`, which now keeps one line per rule and points here.

## Skill usage

- **Check `.claude/skills` (project) and `~/.claude/skills` (global) for a matching skill/convention BEFORE implementing.** Prefer the skill's guidance over improvising.
- Skills surface to the model by their `description`; a skill with no description cannot be chosen. If a relevant skill exists but is malformed, fix it rather than reimplementing its content inline.
- **Always sync the WHOLE skill, never just `SKILL.md`**: every `references/*.md` and `templates/` asset too, then confirm parity per file with `diff -q --strip-trailing-cr`. A bare `diff -rq` between a global root and a repo-local one reports every file as different on Windows, because `.gitattributes` makes one copy CRLF and the other LF: that is a `.gitattributes` fact, not drift. Report parity as "N eol-only, 0 real".
- **Local `.claude/skills/` and global `~/.claude/skills/` reconcile automatically on every `claude-learn` run, both directions, without asking.** Detecting drift and closing the run with "want me to reconcile?" is the failure being corrected: fix it in the same run and report what converged. The size of the drift is a reason to do the work, not a reason to ask. Stop only to avoid deleting or overwriting existing global content, or to keep repo-specific content deliberately divergent (name it, do not ask).
- **Global skills are repo-agnostic.** Repo-specific detail (paths, hosts, slot names, one repo's pipeline) lives in that repo's `docs/` or a local skill, never in a global leaf. A pointer to a global leaf that no longer exists is repointed to the repo doc or to the generic leaf that covers the topic; do not recreate a repo-specific leaf, and do not ask before fixing such technical debt (2026-10-07, bico: `deploy-hetzner-box/references/bico-planner-cicd.md`). Search every file type for the pointer, hooks and scripts included, not only `*.md`.
- **No symbolic links or junctions for skills, agents or commands** (owner, 2026-10-29: "We want no symbolic links … fix that"). `npx skills add -g` without `--copy` made `~/.claude/skills/<name>` a junction into `~/.agents/skills/<name>`; a plugin install's retire of such a skill then failed with `EPERM: operation not permitted, symlink`, because the backup copied the link as a link. All eight junctions became real folders, Claude Harness backs a link up as its files, and its "Link into repo" became "Move into repo". Install with `--copy`; prove it with `Get-ChildItem ~/.claude/skills -Recurse -Depth 2 -Attributes ReparsePoint`, which must list nothing.
- **A `description` is an index entry, not a node**: routing plus trigger phrases, detail in `references/<leaf>.md`. Every description loads on every turn.
- Authoring hygiene in full (manifest casing, frontmatter, name drift, masters versus nested skills, the linter): `context-engineering/references/skill-authoring-hygiene.md`. Budgets and how to measure a trim: `context-engineering/references/graph-engineering.md`.

## Universal preferences

- **YOU MUST NOT create a shared package or library.** No NuGet or npm package, no shared class library, no local package feed, no `Directory.Build.props` carrying shared build settings, and no project referenced across repositories. Duplication between projects and between repositories is the accepted answer and is preferred over any shared package. An issue or a plan that says otherwise is wrong: stop and ask.
- **YOU MUST NOT write documentation unless explicitly asked in that message.** No README, no doc under `docs/`, no guide, no handoff, no doc section appended to a code change, no readme row for a new file. Finishing a feature does not earn a doc. A plan, an issue or a Done when step that asks for a doc does not count as asking: skip that step and say so in the report.
- **NEVER commit — ever — unless the user explicitly tells you to in that message.** Do not auto-push, and do not offer, suggest, or ask to commit at the end of a task. Staging/committing/pushing happens only on an explicit, in-the-moment instruction. **"Override the history" (or rewrite, reset or squash the history) of a pushed branch IS that instruction, for the rewrite and the force push together.** The remote is the copy that leaks, so a local rewrite that stops and asks about the push has not done the job (2026-10-20, audio-star: "we can override history to 1.1.0" was answered with a local root commit and "your call" on the push; the owner's reply was furious). Get `git status` clean first, then push with a lease and verify the remote; procedure in `git-flow-plugin:git-flow`, leaf `git-history-ops`, "Override the history".
- Do **not** delete files unless explicitly asked ("clear" means edit content, not `rm`). Flag deletions for confirmation instead.
- **`git clean` and `git reset --hard` require a dry run and an inventory first.** They destroy what git is not tracking, and no amount of explicit authorization makes that recoverable. Run `git clean -nd <path>`, list what is untracked-and-never-committed versus gitignored working state, and report both to the user before executing. Rescued files must be moved *out* of the tree being cleaned: moving them to another untracked path inside it does nothing, and cost a never-committed project once. Full procedure in `git-flow-plugin:git-flow`, leaf `git-history-ops`.
- **Never remove, redact, mask, or placeholder-out (`<FILL_ME>`) any value in credentials files** (`credentials.json`, `credentials.md`, `.env`, `deploy.json`). They are git-ignored on purpose — real tokens, passwords, IPs, and IDs stay hardcoded there at all times. Only ever ADD or UPDATE values; when restructuring such a file, carry every existing value over verbatim and diff-check before writing. Sanitize docs/examples instead, never the credentials file itself. Add a value by a textual insertion into the working copy (copy the file to the scratchpad first), never by `json.load`/`json.dump` (it reformats every array) and never by rebuilding from `git show HEAD:` (2026-10-07, bico: that rebuild dropped the uncommitted SQL host change in `.github/workflows/credentials.json`; it was restored only from a masked diff).
- **Context marked off-record stays off every persistent surface.** "FYI, don't put this into text" covers more than the file being edited: no doc, no legal clause, no lessons entry, no memory file, no commit message, and no restatement in a later summary or session recap. Such context is given so the work comes out right, not so it gets recorded. Reply with the consequence for the artifact in hand and nothing else, and keep it out even when a later turn makes it feel load-bearing.
- **No auto-memory.** Never write to `~/.claude/projects/*/memory/`, even when a session's system prompt enables auto-memory and tells you to save there. Learnings go to the repo's lessons file (`tasks/lessons.md`), a skill, or `CLAUDE.md`; an open to-do goes to the owning repo's `tasks/` folder. On 2026-10-15 a session wrote four feedback files and a to-do into the memory folder because its system prompt said to; the owner: "memory is prohibited ... we have tasks, learning, harness but no memory". The content had to be moved to lessons and tasks and the memory writes reverted.
- **No em dashes in anything generated** (docs, skills, artifacts, UI copy, commit messages): use a colon, comma, semicolon, or parentheses instead. Verbatim quotes of existing text keep their original punctuation.
- **Every 2026 repo keeps a mandatory `CHANGELOG.md`** (owner, 2026-10-29: "all repos of 2026 have mandtory changelogs", then "from now on ... no need to re-create history"). A repo without one gets it created with the current change only, in Keep a Changelog format under `## [Unreleased]`; earlier history is never reconstructed from `git log`. The git-flow mod asks to ship only once this session's line stands, and claude-learn's task 1c writes it. A build that let a repo without the file ship without a line was exactly the invented exception this rule removes.
- **Repeated workflows are mods with a script, not prose** (owner, 2026-10-29: "i like mod based solutions as they are deterministic", pointing at article-writer). A procedure the owner runs again and again (an article pipeline, the commit, push, PR and merge ending) is a plugin whose hooks module watches the session and whose script makes every decision and prints JSON, so a session without the mod runs the same commands; instructions a model may skip are the fallback, not the design. `mod-authoring` owns how.
- **An empty search result is a claim about the search, not about the repo. Prove the search was aimed correctly before reporting an absence.** This has now caused three separate wrong conclusions across sessions, so it is a rule rather than a caution. The specific mechanism: the working directory is shared between the PowerShell and Bash tools and it **persists**, so a single `Set-Location`/`cd` (typically to build a project) silently repoints every later relative `find`, `ls`, `grep` or `git status` at that subdirectory. The commands still succeed, and a subtree with none of what you asked for returns cleanly empty. Never search relatively after any `cd`: pass an absolute path, or print `pwd` in the same command. Before saying "this repo has no X", re-run once from the repo root with an absolute path, and treat a convention directory the repo already documents (a ledger, a scripts folder, `.claude/skills/`) as the thing you failed to find rather than the thing that does not exist. Inventing a mechanism the repo already has is the usual cost. **The same persisted `cd` breaks writes, not just searches**, and there the failure is louder but easier to miss: a relative `cat >> tasks/lessons.md` after an earlier `cd` into a subdirectory died with "No such file or directory" while the `echo ok` chained after it still printed, so the run looked successful and the append had gone nowhere. Use absolute paths for every write too, and never chain a success echo onto a redirect: read back the tail of the file instead. **And an absolute path has a form per interpreter, not per tool.** The Bash tool is Git Bash, so redirects, `cat`, `ls` and `grep` take `/d/...`; anything it hands to a Windows binary does not, and an inline `python - <<'PY'` block given `/d/...` dies `FileNotFoundError` in the same command where the heredoc above it wrote that exact path successfully. Windows binaries take `D:\...`. Nor is the Bash tool one shell with PowerShell: a here-string (`@'...'@`), `$env:` or a backtick escape inside it is either a parse error or, worse, silently valid as literal text, which is how a commit message becomes wrong without failing. **Two more Git Bash rewrites that read as your mistake rather than the shell's:** MSYS path conversion turns a Windows tool's `/FLAG` switch into a path, so `taskkill /PID 1234 /F` dies on `Invalid argument/option - 'C:/Program Files/Git/PID'` and the switches must be doubled (`taskkill //PID 1234 //F`); and `$TMPDIR` is unset here, so `-o "$TMPDIR/out.json"` silently resolves to `/out.json`. Write the scratchpad path literally. **Never chain a cheap verification onto a long or costly command whose result you need**: a 36-minute run returned `HTTP 200` and was reported as failed because the `wc -c` chained after it inherited that same empty `$TMPDIR` and took the exit code with it. Run the expensive thing alone; inspect its output as a separate step. **And never pipe a background process whose value is what it prints WHILE running**: `... | Select-Object -Last 20` on a backgrounded device-code login held the whole stream until the pipeline finished, so the output file stayed empty, the code never surfaced, and the job died on its own timeout looking as though it had printed nothing. Use `*>&1` and read the output file; `-Last`/`-First` are for foreground commands you only read after they exit. **A persisted `cd` also moves every subagent spawned after it**: one `cd` into a global skill folder, made only to read it, became the session's primary working directory, and a 37-agent workflow launched later ran with that folder as its cwd; only the absolute paths in the brief kept the agents writing into the repo.
- **Answer with the essentials only.** A chat reply is the finding plus the recommendation, in the fewest lines that carry it: a short question gets one or two sentences, a completed task gets what changed and where. Default to prose or a short list; only build a table when the user asked for one or the data is genuinely tabular.
  - Cut by default: restating the request, narrating the steps or tools used, evidence walkthroughs, alternatives not taken, caveats the user did not ask about, follow-up checklists, "next steps", and closing summaries of what was just said.
  - Never pad a reply to look thorough. Length is not a quality signal, and a page-long answer to a short question is a defect. If detail is genuinely needed, put it in the file or artifact being produced, not in the reply.
  - The user can always ask for more. Leaving something out is cheap; making them scroll past it is not.
  - **A blocker is one line, not a status report, and the list of what you did NOT do is not content.** A hand-back read: "The e2e suite has never been runnable. No storageState, no globalSetup, authEnabled: true in all four src/secrets-ui/src/environments/*.ts. That blocks all five rename tests and the two pre-existing list.spec.ts ones. Pick a saved MSAL state or an auth-off local environment and I'll wire it and run them." followed by a paragraph naming every tool that was and was not run. The user's answer was that it bloats them with information they did not ask for. Say the blocker and the one decision needed ("e2e needs an auth mode picked - MSAL state or auth-off?") and stop. The environment inventory, the file count, the tools that produced the evidence and the tools that could not attach are all answers to questions nobody asked; they go in a closing offer at most. Reporting a gate you were told to respect (tests barred, browser not attached) as though it were a finding is the same defect wearing a compliance badge.
  - **Git state is never news.** Do not report what is committed, uncommitted or staged, or what other sessions left uncommitted, unless the message asks for a commit or push: git is the owner's business. A status reports the work, not the working tree (2026-10-23, claude-code-masterclass: a status line counted the plugin folder's changed files and other sessions' uncommitted edits, and a relayed agent report said "nothing was committed"; the owner: git is not my business outside an explicit commit or push request).
  - **A status question gets two or three lines**: what is running or finished and the one number that shows progress. Never sections, headings or a list of everything checked.
  - **"Explain this" is answered in the owner's words.** Say what happens and why it matters to them; leave out internal paths, tool names and mechanism vocabulary. Incident (2026-10-23): asked to explain a guard's open point, the first answer named `Temp\claude\...\tasks\`, "lookup" and "the fact-gatherer reminder", and the owner still did not understand; the second, "if I peek into a helper's working log, the guard treats it as me doing the research myself", landed at once.
  - **Answer the question that was asked, at its own size.** One question gets one answer. Related things found along the way are named in a clause each, never expanded into a ranked list with evidence, and never joined by a "what's good about it" counterweight the user did not request. Offer the detail in a closing line ("want the other three?") instead of delivering it.
