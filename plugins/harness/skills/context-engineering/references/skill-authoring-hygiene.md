# Skill and agent authoring hygiene

Moved verbatim out of `~/.claude/CLAUDE.md`, which keeps the one-line rules and points here. These are the defects that break the menu: a skill that cannot be discovered, or a stray file discovered as one.

When creating or editing a skill or agent, enforce:

- Skill manifest filename is exactly **`SKILL.md`** (uppercase): lowercase `skill.md` breaks discovery on case-sensitive filesystems (Linux/CI).
- Every skill `SKILL.md` and every agent `.md` has YAML frontmatter with a **non-empty `name` and `description`**. The description must carry concrete trigger phrases.
- **A `description` is an index entry, not a node.** One line of routing plus its trigger phrases; capability lists, feature inventories and worked detail go in `references/<leaf>.md`. Every description in the library loads on every turn, including the turns it has nothing to do with, so it is the one place where writing more feels free and is not. Budgets and how to measure a trim: `graph-engineering.md`.
- **A `description` stays at or under 1,024 characters**, the Agent Skills limit; one over it is flagged in the every-session skill list. Bring it under by rewriting, never by a fixed cut that drops the trailing triggers: delete the capability inventory and any "Use when" sentence the triggers already say, merge triggers that mean the same thing ("redraw the logo as vector" + "trace the mark to svg" -> "redraw or trace the logo as svg"), and keep at least one trigger per leaf. Measure: `python -c "import re,io;d=re.search(r'^description: \"(.*)\"$',io.open('SKILL.md',encoding='utf-8').read(),re.M).group(1);print(len(d))"` (2026-10-28: 1,699 -> 969 with every leaf still reachable).
- `name` in frontmatter matches the folder/file identity (no drift).
- Agent and skill descriptions describe **this** repo's project and paths: never leave a description copied from another repo (a mis-scoped description means auto-routing never matches).
- **A global skill is project-agnostic in the body, not only in the description.** No repo names, no absolute local paths, no "reference implementations" list of the projects that used it. They rot, they leak one client's work into another client's context, and they push the reader toward copying a project instead of following the rule. Name an upstream by its role ("the site's Hugo source tree"), and replace a per-project list with the general rule it was trying to illustrate. Local `.claude/skills/` is where this repo's surfaces get named.
- **The same holds for a skill's `templates/` and `scripts/`.** A script hard-wired to one repo (absolute paths, a font, a word, a pixel band) gets a CONFIG block of placeholders, and the repo's real values move to that repo's `.claude/rules/` file, which names the script. Prove the refactor kept the behaviour by running the old copy (an installed plugin's cache still holds the previous version) and the new one on the same input and diffing the outputs: identical bytes or pixels, or it changed something. `python -I <this skill>/scripts/compare-script-versions.py --old <old> --new <new> --set "NAME=<value>" --compare <old out> <new out> --work <scratch>` does it and ends with `output_equal=`.
- Don't reference a skill/agent by a name that doesn't exist (no name drift between `CLAUDE.md` and the actual folders).
- **A master skill's leaves are always references, never nested subskills.** A master holds exactly ONE `SKILL.md` at its root (the router); every leaf is a plain `references/<leaf>.md` with **no `name`/`description` frontmatter** (frontmatter is what makes a stray file get discovered as a skill), and shared assets live under a sibling `templates/`. The router delegates by telling the model to READ `references/<leaf>.md`, never by a `Skill` call. **Never nest a `SKILL.md` inside another skill's folder.** If a capability genuinely must be independently auto-discoverable, promote it to its own top-level peer skill folder (`.claude/skills/<name>/SKILL.md`), not a nested one.
- **No dollar sign followed by a digit in a `SKILL.md` body.** The Skill tool substitutes positional arguments (`$0`, `$1`, ...) when it loads a skill, so every such token arrives replaced by a word of the caller's arguments or by nothing. Prices like `$1/day` reached agents as "Module/day", `$1 to $0` as "over to Pass", and an awk field `{print $2, $3}` loses its fields. Write prices as `USD 1`, awk fields as `$(2)`, spreadsheet references without a dollar before the row, and keep scripts that need positional parameters in `scripts/` or a `references/` leaf, which load through Read and are left as written. Prove it with `grep -nE '\$[0-9]' <skill>/SKILL.md`, which must print nothing (2026-10-20).

Run `bash ~/.claude/scripts/lint-claude-config.sh <repo>` to catch these (it flags nested `SKILL.md` manifests and reference files that carry discovery frontmatter).

## A bundled asset is a cache, never a source

A skill that ships a binary (a logo, a wordmark, a font, a template file) holds a **copy** of something another repo owns. The copy goes stale silently: nothing in the skill changes when the upstream does, so the skill keeps looking authoritative while shipping a superseded asset, and the defect only surfaces after it has gone live somewhere.

- **Every bundled asset names its upstream in `SKILL.md`**: the file path in the owning source tree, plus which side wins when they disagree (it is always the upstream). A download URL is not enough; it says where the bytes came from, not who decides what they should be.
- **Re-verify against the upstream before using it**, not just before editing the skill. Diff the asset and re-read the markup/CSS that renders it there.
- **Port the upstream's own styling verbatim rather than re-deriving the look.** Numbers in a lockup are usually derived from the asset's canvas, so a re-derived value can look right and still break the alignment the asset was padded to produce.
- **State the invariants the asset must keep** (what may be recoloured or re-set, what is composited 1:1 and never touched), so a later pass does not "improve" fixed brand material.

## Syncing a skill

**Always sync the WHOLE skill, never just `SKILL.md`.** Any copy, push (local -> global), pull (global -> local), reconcile, or move of a skill operates on the entire skill folder: the root `SKILL.md`, every `references/*.md`, and every `templates/` asset. Diff recursively (`diff -rq <src> <dst>`) and confirm parity after; a leaf or template left behind is a broken skill. Never sync the manifest alone.
